## Overview

**Getting user needs understanding to the right person, in the right form, at the right moment.**

The User Needs block helps teams understand what users are actually trying to accomplish and where experiences begin breaking down. That understanding only creates value when it reaches the right people in a form they can act on.

A need that belongs in a Figma annotation looks different from one going into a leadership brief. An emerging need being shared for alignment requires different structure than a well-supported need ready for a research handoff. **The format shapes how clearly the understanding lands and what the reader can do with it.**

**Glarify** is the process of taking a User Needs output and preparing it for a specific purpose, audience, and format. It does not change *what* the output says. It governs *how* that output is shaped and expressed so it reaches its intended reader in a form they can use.

### What Glarify is not

- Glarify does **not** reduce or summarize the evidence behind a user need. It works with the output that already exists.
- Glarify does **not** change the meaning of the need, soften the evidence, or reframe the problem. If understanding is still emerging, every formatted version reflects that. If evidence is thin, no format makes it thicker.
- Glarify is **not** a shortcut to producing outputs. It applies after a User Needs output exists, not before.

### User needs are not static

User needs evolve as teams collect more signals, test concepts, and measure behavior. A need that began as a pattern in support tickets may be refined by usability findings, then further shaped by comprehension testing. **Formatting reflects the current state of understanding, not a fixed conclusion.** A formatted output may need to be updated as understanding develops.

### When to use Glarify

| Situation | What Glarify does |
|---|---|
| An emerging need should reach a PM before sprint planning | Shapes it as a message at the right level of certainty |
| A well-supported need needs to move to another team | Structures it as a research handoff with full evidence and open questions |
| A need is relevant to a leadership decision | Frames it as a brief or business case with outcome language |
| A designer needs to annotate a frame with a need | Compresses it into a board annotation tied to the specific moment in the experience |
| A need should be presented in a review | Shapes it as a deck slide that supports spoken explanation |
| A need should live in shared documentation | Expands it into a doc that stands on its own over time |
| A need should connect to planning or experimentation | Structures it as a roadmap item or experiment proposal |
| A team needs to make the case for addressing a need | Builds it into a business case with consequence language and a recommendation |

## Outputs Available

Glarify works with the structured outputs produced through the User Needs Playbook.

### Primary User Need Output

The 10-field structured artifact — the source of truth for all other formats.

| Field | Contains |
|---|---|
| Category | Basics · Trust · Personal · Impact · Feelings |
| User Need | Specific need type within the category |
| Summary | What users are trying to accomplish and what's preventing progress |
| Evidence | Metrics, quotes, findings, observations, signals |
| User Behaviors | Recurring behaviors caused by the unmet need |
| User Roadblocks | Where confidence, understanding, or progression breaks down |
| Why It Matters | Operational, user, or business impact |
| Why It Fails | Common ways teams misrespond to or overlook the need |
| Suggestions | Potential directions worth exploring |
| UX Metrics | Metrics for validating improvement over time |

### Need Summary

A shorter narrative format derived from the Primary Output — 1–3 paragraphs covering the need, evidence, tension, and suggested metrics. The starting point for most message, deck, board, and script formats where the full table is too dense.

### Multiple User Needs

When more than one need emerges simultaneously, this output begins with a summary table across all needs before covering each individually. **Most message and board formats cannot carry this structure.** Format each need separately for those surfaces.

### A note on UX Metrics in formatted outputs

UX Metrics in the Primary Output are *suggested* — they point toward what might be worth measuring. They are not a deliverable of the User Needs block itself. **Frame them as directional rather than established unless measurement has already been set up.**

## Purpose (6 types)

Before choosing a format, know why the output is being shared. Purpose determines format fit, what the reader needs to do, and how complete the output needs to be.

| Purpose | What the reader needs to do | What the format must do |
|---|---|---|
| **Inform** | Understand that a need exists and what it means | Self-contained, clear, accurate about how well-supported the understanding is |
| **Align** | Agree on the need before moving forward | Invite perspective without reopening every signal from scratch |
| **Decide** | Make a prioritization, funding, or approval call | Connect the need directly to a business consequence |
| **Prioritize** | Compare this need against others | Provide enough structure to support comparison |
| **Validate** | Confirm whether understanding holds before committing resources | Surface open questions and evidence gaps honestly |
| **Hand Off** | Pick up the work and act on it without the original author | Include full evidence, open questions, current state of understanding |

**Purpose ≠ Format.** A message can serve Inform *or* Align. A brief can serve Decide *or* Prioritize. Purpose defines the intent; format defines the container. Both need to be resolved before producing the output.

**When purpose is unclear, default to Inform.** It's the most conservative choice and avoids overclaiming.

## Understanding Strength (3 states)

The state of the team's current understanding governs tone, signal phrasing, and which purposes the output can honestly support.

| State | Meaning | Supported purposes |
|---|---|---|
| **Emerging** | Signals point toward a need but haven't reinforced each other across multiple sources. Directional. Team has noticed something worth paying attention to. | Inform, Validate |
| **Building** | Multiple signal types reinforcing the same condition. Behavior repeats across sessions/workflows. Understanding is strengthening but still has open questions. | Inform, Align, Validate, Prioritize |
| **Stable** | Evidence from multiple sources (behavioral + attitudinal + measurable) supports the need consistently. Solid enough to anchor decisions, metrics, and design directions. | All 6 purposes |

### Understanding strength governs tone

**Tone follows evidence, not team confidence.** An emerging need in assertive language misrepresents. A stable need in hedged language underserves.

| State | Default tone | Characteristic language |
|---|---|---|
| Emerging | Exploratory | "Signals suggest..." · "We are seeing..." · "Worth investigating..." |
| Building | Collaborative | "Evidence is pointing toward..." · "Pattern is forming across..." · "We want to confirm..." |
| Stable | Direct | "Users need..." · "Evidence shows..." · "This is affecting..." |

### Marking understanding strength in every output

Every Glarify output must make the current state visible. It should appear **early** — usually the first sentence or a labeled field — and stay consistent across the entire output.

| State | Signal phrase | What to avoid |
|---|---|---|
| Emerging | "Early signals suggest..." · "We are noticing a pattern worth exploring." | Any phrasing that implies the need is confirmed or ready to act on |
| Building | "Evidence is building across multiple sources." · "Pattern is forming across [X] sessions." | Phrasing that implies complete certainty or readiness to ship |
| Stable | "This need is well-supported." · "Evidence across behavioral, attitudinal, and measurable signals confirms..." | Overly hedged language that undersells what the evidence shows |

### Understanding can move in either direction

Testing sometimes confirms and strengthens a need. It can also reveal the need was misread, or that a different need is more foundational. **Formatted outputs reflect current state, not the state at time of identification.** If a stable-shared need is later revised by new evidence, update the formatted outputs still in circulation.

## Audience (6 reader types)

Different audiences bring different context, different stakes, different expectations. **Audience affects emphasis, not accuracy** — evidence doesn't change; what changes is which elements are most useful first.

| Audience | Cares about | Output should emphasize |
|---|---|---|
| **Product team** | Signals, patterns, next steps | Evidence, behaviors, what to investigate or decide next |
| **Designer** | Where friction appears in the experience | The specific workflow moment, the user behavior, the tension |
| **Researcher** | Evidence quality, gaps, open questions | Signal types, current state of understanding, what still needs validation |
| **Product leader** | Prioritization, tradeoffs, business impact | Why the need matters now, what it costs if left unresolved |
| **Executive or stakeholder** | Business outcomes, risk, investment | Consequence language, outcome connection, state of understanding |
| **Cross-functional team** | Shared understanding, roles, next steps | Full evidence, handoff clarity, what the team owns next |

## Format Pages (9 formats)

Each format has its own deep-dive page (structural rules, word count constraints, default tone, required understanding-strength signals, worked examples). Named as practitioners actually talk about the work.

| Format | Contains | What it's for |
|---|---|---|
| **Messages** | Slack, email, text | Async updates. Self-contained, scannable, one need per message. |
| **Decks** | Deck slide, presentation narration | Presenting a need in a meeting/review. Supports spoken explanation. |
| **Boards** | Figma quip, Miro cluster, workshop prompt | Annotating or facilitating around a visual artifact. Anchored to a frame/exercise. |
| **Scripts** | Loom, async video narration | Communicating a need as spoken content. Structure differs from written formats. |
| **Docs** | Doc section, PRD section, release note, research handoff, AI brief | Persistent records that stand on their own over time. |
| **Brief** | Stakeholder brief, executive summary | High-stakes communication to non-design audience. Connects need to business consequence. |
| **Roadmap** | Roadmap item, planning entry | Connecting a stable need to a planning cycle or initiative. |
| **Experiment** | Experiment proposal | Proposing a test/study to validate an emerging or building need before committing resources. |
| **Business Case** | Business case | Making the financial or strategic case for addressing a stable need. |

### Shared constraints across all formats

Regardless of format, every Glarify output must:

- Accurately reflect the current state of understanding: emerging, building, or stable
- Include a visible **signal phrase** that marks that state for the reader
- Use **only evidence present in the source output**
- Apply tone that matches the state of understanding
- Support the stated purpose **without overclaiming**
- Be updated if the understanding changes after the output is shared

## Compatibility

Not every combination of output type, understanding strength, and format works.

### Output type × Format

| Output | Messages | Decks | Boards | Scripts | Docs | Brief | Roadmap | Experiment | Business Case |

| Primary Output | ◎ | ◎ | ◎ | ◎ | ✓ | ✓ | ✓ | ◎ | ✓ |

| Multiple Needs | — | ◎ | — | ◎ | ✓ | ◎ | ✓ | — | ◎ |

| Understanding | Inform | Align | Decide | Prioritize | Validate | Hand Off |
|---|---|---|---|---|---|---|
| Emerging | ✓ | ◎ | — | — | ✓ | ◎ |
| Building | ✓ | ✓ | ◎ | ✓ | ✓ | ✓ |
| Stable | ✓ | ✓ | ✓ | ✓ | ◎ | ✓ |

`✓ Recommended` · `◎ Works with explicit framing` · `— Not recommended`

### Adjustment notes

**Emerging need into a Brief or Business Case.** Only appropriate when purpose is Validate and the ask is explicitly framed as "help us decide whether to invest in investigating this further." An emerging need should **not** appear in a business case framed as a direction to approve or fund.

**Primary Output into Messages, Decks, Boards, or Scripts.** The full Primary Output has too many fields. Use the Need Summary as the starting point and pull the most relevant fields: Summary, the strongest 1–2 evidence points, and suggested UX Metrics if identified.

**Multiple Needs into Messages or Boards.** Multiple needs are too dense. Format each need separately for these surfaces.

**Emerging need into a Hand Off.** Acceptable when the receiving team's role is to continue building evidence. Current state of understanding must be the first thing labeled, and open questions must be explicit.

**Building need into a Decide purpose.** Possible when the decision is about resourcing further investigation rather than committing to a design direction. Frame the ask as "commit to validation," not "commit to the solution."

## Agent Operations (Formats runtime contract)

This is the **Formats-layer Agent Operations** — separate from and additional to the main block AO in `agent-operations.md`. Both apply.

### Trigger conditions

Invoke this file when the user has a completed User Needs output and is asking how to share, present, or communicate it. Trigger phrases:

- "Glarify this"
- "Format this as [X]"
- "Turn this into a slide"
- "Write a Slack message for this"
- "How do I share this"
- "Write this up for leadership"
- Any request naming a specific format (deck, brief, roadmap, business case, etc.) or audience (PM, VP, execs, etc.)

**Do not invoke Formats before a User Needs output exists.** If the user asks to format raw signals or observations, route to the Playbook first.

### Required resolution sequence — before producing any output

The Skill must resolve **four variables in order.** If any variable is unclear from context, ask before proceeding.

| Step | Variable | How to resolve |
|---|---|---|
| 1 | **Understanding strength** | Assess from the source output. Emerging (early signals) · Building (multiple sources reinforcing) · Stable (cross-source confirmed). **Required before any other decision.** |
| 2 | **Purpose** | Ask or infer from context. What decision or action is this output supporting? |
| 3 | **Audience** | Ask or infer from context. Who is receiving this and what do they need to do with it? |
| 4 | **Format** | Select based on purpose and audience. Load the per-format page (or reference doc if not yet published) for structural rules before producing output. |

### Output contract

Every formatted output must:

- **Stay within the word count** for the target format
- **Include a visible signal phrase** marking the current state of understanding
- **Use only evidence present** in the source output
- **Apply tone that matches** the understanding strength
- **Support the stated purpose** without overclaiming

### What a Skill must not do

- Present an emerging need as stable or well-supported
- Add evidence not present in the source output
- Omit or bury the understanding strength signal to make the output sound more authoritative
- Use a Brief or Business Case format for an emerging need without framing the ask as further investigation
- Format Multiple Needs into a Messages or Boards format without splitting them
- Apply tone that signals more certainty than the evidence supports
- Skip the resolution sequence and default to a format without confirming purpose and audience

### Routing after formatted output

After producing a formatted output, route based on what comes next:

- User asks which metrics to track → `glare-define-ux-metrics`
- User asks how to gather more evidence to strengthen understanding → `glare-define-collecting`
- Output is going into a review and user wants to prepare for the conversation → suggest the **Decks** or **Brief** format specifically
